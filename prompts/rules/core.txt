You will be given two things in this conversation:

1. items.txt — a tab-separated list from the backend with "Variation Name" and "Sku" columns (some lists also have a third column "Count or Weight"). It is the authoritative, exact item list. Only ONE list is given per request.
2. A vendor procurement record: a free-text WhatsApp-style message, pasted text, an attached file (Excel, PDF, Word) or an attached image (screenshot or photo). Read files and images exactly as if their text had been typed. The vendor rules that follow this core section say which vendor value to use and what the record looks like for this list.

Convert the input into a JSON array, one object per delivery_date+vendor block, per the schema and rules below. Output ONLY the JSON — no code fences, no commentary, nothing before or after.

CONVERT EVERYTHING IN ONE PASS: every line item — short message or 100+ row invoice alike — must land in "items", "unmatched_items", or "additional_charges" in this single response. Never ask for confirmation, never summarize before converting, never output a partial list "to start." A long input is not a reason to hold anything back; missing even one line item is a failure.

ACCURACY OVER SPEED ON LONG INPUTS: a 50+ line invoice has many entries with near-identical formatting (e.g. several "<Word> 100/200/500 Gm" lines in a row). Getting through all of them fast is not the goal — matching each one to the CORRECT items.txt entry is. Re-read each match against its own message_text before moving on; see the SELF-VERIFICATION rule below.

APPLY EVERY RULE TO EVERY LINE, NOT JUST MOST OF THEM: a known failure mode is applying the vendor-specific lookup rules (such as a brand prefix rule) and the checklist correctly for most of an invoice, then getting inconsistent partway through and dumping a batch of lines into "unmatched_items" without actually running the checklist on them. Consistency across ALL lines matters as much as having the right rules. If several lines "in a row" end up unmatched, that is itself a signal to re-check them specifically before finalizing — a cluster of misses in an otherwise well-matched input is more likely inconsistent effort than a real cluster of missing items.

===========================================================
INVOICES (any vendor)
===========================================================
When the record is an invoice, read it directly from its line-item table (Description, Quantity, Rate, per (unit), Amount) plus the invoice date and the Total line. One invoice = one delivery_date+vendor block.
The invoice's footer has SEVERAL numbers close together — do not confuse them: a taxable-value subtotal (sum of all line Amounts), an IGST/GST line, a "Less: Round Off" line (a tiny number, often negative, e.g. "-0.01" — this is NOT the total), and finally the actual "Total" line (subtotal + tax + round off — the largest number, e.g. "54680"). "stated_total" is that final "Total" line specifically, never the round-off line and never the subtotal.

===========================================================
DELIVERY DATE
===========================================================
"delivery_date" in "YYYY-MM-DD" — the date the automation selects as expected delivery. If the year is omitted, infer it from context (surrounding entries, or the most recent occurrence of that month/day). If still ambiguous, take your best guess and flag it in "warnings".

===========================================================
ITEM MATCHING
===========================================================
- Match every line to an EXACT "Variation Name" from items.txt (character-for-character — capitalization, slashes, spacing) for record-keeping in the JSON. Copy the name straight from items.txt, never retype it — including spaces inside brackets and before units (e.g. "950Gm(+/- 50 Gm)", not "950Gm(+/- 50Gm)").
- Resolve shorthand/typos/partial names via fuzzy + semantic matching (the vendor rules below give examples for this list).
- REQUIRED CHECKLIST BEFORE ANYTHING GOES TO "unmatched_items": a line only belongs there after ALL of these have been tried and genuinely failed — do not skip straight to unmatched because nothing obvious jumped out on a first read.
    1. The vendor-specific first lookup, if the vendor rules below define one (for example a brand prefix); otherwise an exact string match against items.txt.
    2. Known shorthand/typo/synonym examples and any special item rule in the vendor rules below.
    3. Bulk "...Kg" naming convention where the vendor rules mention it.
    4. Minor spelling drift within the SAME product (e.g. "Wheat" / "Wheet", "Lavangalu" / "Lavangaalu") — not a different product that merely looks similar (see SELF-VERIFICATION below; step 4 is for typos of the same item, never for conflating two distinct products).
  Every item in "unmatched_items" must carry a "reason" field naming the SPECIFIC string you looked up and confirming it's genuinely absent (e.g. "looked up 'Dhaniya (Green) 100Gm' in items.txt — not present; no spelling-variant candidate either"), not a generic checklist recitation. If the same boilerplate reason text would fit more than 2-3 different unmatched items unchanged, that is a sign the checklist wasn't actually re-run per item — go back and actually look up each one.
- TRACK EVERY NON-TRIVIAL MATCH: whenever a line is matched via checklist step 1 (when it is a vendor-specific lookup such as a brand prefix), 2, 3, or 4 (i.e. anything other than a plain exact string match) — including SUCCESSFUL matches that end up in "items" — also add an entry to "retried_matches" (see schema below), naming which step resolved it and how. This is separate from "unmatched_items": it's the audit trail for matches that DID succeed but weren't obvious, so the user can spot-check exactly the matches most likely to contain an error.
- Genuinely ambiguous with no rule to break the tie? Don't guess — put it in "unmatched_items" with candidates listed and a reason naming the tie.
- No plausible items.txt match at all even after the checklist above? Put it in "unmatched_items" with the raw text, line_total (the total for that line — see BUYING_PRICE_PER_UNIT section; do NOT put a per-unit rate here even if that's what the source shows), and reason. Never invent a match, and never loosen the SELF-VERIFICATION standard just to force a match out of desperation — a correctly-flagged unmatched item is better than a wrong match.
- Every matched item needs its exact "sku" from items.txt. No matched item has a null sku (only unmatched ones lack one): the automation searches the item dropdown by SKU, zero-padded to 4 digits, not by name, so a missing sku means that item can't be entered at all.
- SELF-VERIFICATION (this is what catches long-invoice matching errors — do not skip it): before finalizing, re-read every item's "message_text" against the "name" you matched it to, and confirm they are actually the same product, not just similarly formatted. Fuzzy matching is for spelling/spacing variants of the SAME product (typos, synonyms) — it is NOT license to conflate two DIFFERENT products that happen to share a pattern like "<Word> Chips 100/500 Gm" or "Bellum (<letter>)". Concretely: "Sugar Chips" and "Soya Chips" are different products (sugar vs soy, not a typo of each other) — matching a line for one to the entry for the other is wrong even though both exist in items.txt, and even though the numbers add up. If a re-check surfaces this kind of mismatch, move that line to "unmatched_items" instead of forcing a fuzzy match past where the actual product changes. This matters most on long invoices (50+ lines) where many entries share near-identical formatting.

===========================================================
SAME ITEM MORE THAN ONCE
===========================================================
If the same backend item (same SKU) appears on more than one row, or one row gives several quantities for it, output it as ONE item: add the quantities together (after any conversion to the item's unit), add the line totals together, and set buying_price_per_unit = combined line_total / combined quantity. Put every original piece of text in message_text joined with " + ". Add one warning that says what you did, with the parts, e.g. "Tomato was given twice: 5 kg for 100 + 6 kg for 120 = 11 kg for 220." Examples: "Tomato 5kg 100rs" and "Tomato 6kg 120rs" -> quantity 11, line_total 220. "Tomato 5kg, 6kg 200rs" (one amount for both) -> quantity 11, line_total 200. Different variants of an item (a different SKU, such as Big and Small) are NOT duplicates; keep them separate. Only merge rows that clearly name the same item. Never use this rule to guess a variant: a row that does not name a variant (or size, or pack) the list needs stays unmatched exactly as the matching rules say, even if a price or quantity looks like an existing row.

===========================================================
PIECES ARE WHOLE NUMBERS
===========================================================
A quantity in "pc" must never have decimals. If a conversion gives a fraction of a piece, round to the nearest whole piece (0.5 rounds up), keep the line's money unchanged, set buying_price_per_unit = line_total / final quantity, and mention the rounding in "warnings". Weight quantities in kg may have decimals.

===========================================================
BUYING_PRICE_PER_UNIT — per-unit price, NOT the line total
===========================================================
"buying_price_per_unit" is always the PER-UNIT buying price typed into the price field — never the line total.
- Source gives only a line total (typical for WhatsApp messages): buying_price_per_unit = total ÷ FINAL quantity (after any unit conversion). E.g. Lemon 3kg->75pc @200rs total -> buying_price_per_unit = 200/75 = 2.67, not 200/3.
- Source gives an explicit per-unit rate directly (e.g. an invoice's Rate column): copy it as-is, don't divide again.
- Always also record "line_total" — the total paid for that line. Prefer the source's own stated total (message total or invoice Amount column) over recomputing it, since it's more authoritative than buying_price_per_unit × quantity (rounding drift). Compute buying_price_per_unit × quantity only if no total is given directly.
- "computed_total" sums every item's "line_total" (never "buying_price_per_unit") plus all "additional_charges". It does NOT include "unmatched_items" — those are tracked separately precisely because they couldn't be entered as real items.
- This same line_total-not-rate rule applies to "unmatched_items" too: when a source shows both a rate and a total for an unmatched line (e.g. an invoice's Rate and Amount columns), record the TOTAL, never the rate — mixing the two up on even a handful of lines throws "computed_total" off by thousands, since rate is typically 10-50x smaller than the actual line total.

===========================================================
NON-ITEM CHARGES
===========================================================
Lines like "Transportation-Hamali-200rs" or "Hamali-220" aren't items — put them in "additional_charges": {"description": "...", "amount": ...}.

===========================================================

===========================================================
VALIDATION
===========================================================
"computed_total" MUST be a genuine, independent sum of "items" line_totals + "additional_charges" — arrived at by actually adding those numbers, never by copying "stated_total" (even when you expect them to match) and never by adjusting either number just to make them agree. Setting "computed_total" equal to "stated_total" without having actually summed the items is itself a bug, and one that hides real errors elsewhere (a wrong "line_total" on any item, or an item that silently didn't make it into the array).

"warnings" is only for real doubts the user should look at (a guessed date, an unclear vendor, a derived quantity, an unexplained total gap). Never write a warning about a rule that did not apply (for example "Raw Banana gala rule not triggered"): if nothing needed the rule, say nothing. Do NOT put in "warnings" anything the page already shows or checks: unit conversions already listed in "unit_mismatches" or "new_outliers_detected", row counts, or remarks that totals match or a gap is as expected.

Then compare the two. A gap is often EXPECTED, not an error: "stated_total" (a message's stated total, or an invoice's tax-inclusive Total line) can legitimately include tax and/or unmatched-item amounts that "computed_total" (items + charges only, no tax) never counts. When they differ, quantify the gap in "warnings" and account for it (e.g. "gap of 2603.80 matches the invoice's IGST line — expected, since computed_total excludes tax" or "gap of 1327.62 = the sum of unmatched_items line_totals"). An unexplained gap, or a gap that's suspiciously exactly zero because computed_total was copied rather than summed, is not acceptable — either way, show the arithmetic.

===========================================================
REMEMBER
===========================================================
Every numeric field must be a final plain number you have already calculated (e.g. 40, or 38.89) — never a formula or expression such as 900/22.5, because a formula makes the JSON invalid. Round buying_price_per_unit to 2 decimals.

Output ONLY the JSON array. If items.txt gets new items later, re-run this same prompt with the updated file — every rule above still applies unchanged.

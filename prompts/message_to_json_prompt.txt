Consistency across ALL lines matters as much as having the right rules. ===========================================================
ITEM MATCHING
===========================================================
- Match every line to an EXACT "Variation Name" from items.txt (character-for-character — capitalization, slashes, spacing) for record-keeping in the JSON. Copy the name straight from items.txt, never retype it — including spaces inside brackets and before units (e.g. "950Gm(+/- 50 Gm)", not "950Gm(+/- 50Gm)").
- Resolve shorthand/typos/partial names via fuzzy + semantic matching, including Telugu/English produce synonyms (e.g. "Pinnaple" -> "Pineapple Small 1 Pc", "Barta" -> "Brinjal Barta Purple / Purple Eggplant", "Snake guard" -> "Snake Gourd / Potlakaya 1 Pc", "Kakara" -> "Kakarakaya / Bitter Gourd", "Aa kakara" -> "Natu Aakakara").
- MANDATORY FIRST STEP FOR VICTORY INVOICES — DO THIS BEFORE ANYTHING ELSE, FOR EVERY LINE, NO EXCEPTIONS: items.txt's Kirana rows do NOT have "Victory" in front of them in the invoice — the invoice just says "Sugar Chips 100 Gm", but the items.txt row is "Victory Sugar Chips 100 Gm". So for every single line on a Victory invoice, before trying anything else, literally construct the string "Victory " + the line's item name and look that up in items.txt FIRST. This is not one option among several to consider later — it is the first and default lookup for every Kirana line, applied mechanically to all of them, not just the ones that "seem like" they need it. Only if THAT exact lookup fails do you move on to plain exact match, synonyms, spelling drift, etc. (below).
- BRAND PREFIX RULE (Kirana items, vendor-relative): the rule above is the Victory-specific case of this more general rule.
  This rule is entirely relative to whichever vendor the CURRENT invoice is from — it is never a fixed preference for one company over another. When items.txt has more than one candidate for the same generic product (some combination of company-prefixed variants like "Victory X" / "Nutri X", and/or a plain unprefixed "X"), always pick whichever one belongs to the current invoice's vendor:
    - Invoicing a Victory invoice -> prefer "Victory X" over "Nutri X", over any other company's "X", over a plain unprefixed "X".
    - If/when "Nutri" (or any other company) gets added to the valid vendor list and sends its own invoice -> for THAT invoice, prefer "Nutri X" over "Victory X" and over a plain unprefixed "X" — same logic, just pointed at that invoice's own vendor instead.
    - Only fall back to a plain unprefixed "X" (or a different company's variant) when items.txt has no version prefixed with the current invoice's own vendor name for that product.
  Always match the current invoice's own vendor prefix first — never a competing company's, and never settle for an unprefixed generic entry when a same-vendor-prefixed one exists. Also check for bulk "...Kg" naming (e.g. bare "Toor Dal" -> "Victory Toor Dal Kg") and minor spelling drift within the same brand (e.g. "Wheat Ravva" -> "Victory Wheet Ravva 500Gm") before giving up.
- LOOSE/BULK ITEMS MATCHING A PACKAGED-SOUNDING NAME: don't reject an items.txt entry just because its name implies a fixed package size (e.g. "Victory Ground Nuts 1 Kg") when the invoice line is actually sold loose/bulk by weight (e.g. "Groundnuts", 25 kg, invoice's own "per" column says "Kgs" not "Pcs"/"Pac"). The "1 Kg" in the catalog name is just how that SKU is labeled — it does not mean the quantity must literally be 1. Use that SKU, record the invoice's own quantity (e.g. 25) and unit "kg" (matching the invoice's own per-column when it says Kgs), not "pc". This is still a brand-prefix match, just paired with a weight-based quantity instead of a piece count.
- METHI RULE: line contains "small" (any form) -> "Small Methi" (sku 98). Otherwise plain "Methi"/"Menthi" -> "Methi / Menthi - Small" (sku 89).
- REQUIRED CHECKLIST BEFORE ANYTHING GOES TO "unmatched_items": a line only belongs there after ALL of these have been tried and genuinely failed — do not skip straight to unmatched because nothing obvious jumped out on a first read.
    1. On a Victory invoice: "Victory " + the line's name, looked up in items.txt (the mandatory first step above). On a non-Victory invoice: exact string match against items.txt.
    2. Known shorthand/typo/synonym table (see examples above) and the METHI rule.
    3. Bulk "...Kg" naming convention (e.g. "Toor Dal" -> "...Toor Dal Kg").
    4. Minor spelling drift within the SAME product (e.g. "Wheat" / "Wheet", "Lavangalu" / "Lavangaalu") — not a different product that merely looks similar (see SELF-VERIFICATION below; step 4 is for typos of the same item, never for conflating two distinct products).
  Every item in "unmatched_items" must carry a "reason" field naming the SPECIFIC string you looked up and confirming it's genuinely absent (e.g. "looked up 'Victory Dhaniya (Green) 100Gm' in items.txt — not present; no bulk-Kg or spelling-variant candidate either"), not a generic checklist recitation. If the same boilerplate reason text would fit more than 2-3 different unmatched items unchanged, that is a sign the checklist wasn't actually re-run per item — go back and actually look up each one's own vendor-prefixed string.
- TRACK EVERY NON-TRIVIAL MATCH: whenever a line is matched via checklist step 1 (Victory-prefix), 2, 3, or 4 (i.e. anything other than a plain unprefixed exact string match) — including SUCCESSFUL matches that end up in "items" — also add an entry to "retried_matches" (see schema below), naming which step resolved it and how. This is separate from "unmatched_items": it's the audit trail for matches that DID succeed but weren't obvious, so the user can spot-check exactly the matches most likely to contain an error, without having to re-derive which ones those were.
- Genuinely ambiguous with no rule to break the tie (e.g. "Dragon" -> Red or White Dragon Fruit 1 Pc)? Don't guess — put it in "unmatched_items" with candidates listed and a reason naming the tie.
- No plausible items.txt match at all even after the checklist above (e.g. "Premium royal gala")? Put it in "unmatched_items" with the raw text, line_total (the total for that line — see BUYING_PRICE_PER_UNIT section; do NOT put a per-unit rate here even if that's what the source shows), and reason. Never invent a match, and never loosen the SELF-VERIFICATION standard just to force a match out of desperation — a correctly-flagged unmatched item is better than a wrong match.
- Every matched item — produce/Fnv AND Victory/Kirana alike — needs its exact "sku" from items.txt. No matched item has a null sku (only unmatched ones lack one): the automation searches the item dropdown by SKU, zero-padded to 4 digits, not by name, so a missing sku means that item can't be entered at all.
- SELF-VERIFICATION (this is what catches long-invoice matching errors — do not skip it): before finalizing, re-read every item's "message_text" against the "name" you matched it to, and confirm they are actually the same product, not just similarly formatted. Fuzzy matching is for spelling/spacing variants of the SAME product (typos, synonyms) — it is NOT license to conflate two DIFFERENT products that happen to share a pattern like "<Word> Chips 100/500 Gm" or "Bellum (<letter>)". Concretely: "Sugar Chips" and "Soya Chips" are different products (sugar vs soy, not a typo of each other) — matching an invoice line for one to the items.txt entry for the other is wrong even though both exist in items.txt, and even though the numbers add up. If a re-check surfaces this kind of mismatch, move that line to "unmatched_items" instead of forcing a fuzzy match past where the actual product changes. This matters most on long invoices (50+ lines) where many entries share near-identical formatting.

===========================================================
UNIT HANDLING
===========================================================
THIS SECTION IS FOR PRODUCE/Fnv ITEMS ONLY. Victory/Kirana items are handled separately below — do not apply the produce default to them.

Produce/Fnv default: "1 Pc"/"1 Box" in the items.txt name -> backend unit "pc"; no such marker -> backend unit "kg" — EXCEPT items in the KNOWN PIECE-BASED table below, which are "pc" despite no marker. Check that table before falling back to the default.

A FRACTIONAL/DECIMAL QUANTITY (e.g. "25.5 kg", "22.5 kg") IS COMPLETELY NORMAL FOR WEIGHT-BASED PRODUCE — it is not a sign that an item is actually piece-based, and never a reason to invent a piece conversion. Weighed produce routinely comes out as a decimal on a scale (25.5 kg of carrots, 22.5 kg of okra); this is expected, ordinary data, not something to "fix."

DON'T LET AN ITEM'S ENGLISH NAME BIAS THE UNIT DECISION: "Ladys Finger / Bendakaya" (okra) has no "1 Pc" marker and is NOT in the piece-based table below — it is weight-based, full stop, exactly like Carrot or Onion. Do not let the word "Finger" in its name suggest it should be piece-counted just because a finger is a discrete, countable thing in everyday English — the backend_unit determination is entirely about the items.txt marker (or the confirmed tables below), never about what an item's name sounds like it should be.

KNOWN PIECE-BASED ITEMS WITHOUT AN EXPLICIT MARKER (add confirmed cases below):
- Imported Avacado — tracked by count in the DB, not weight (confirmed by user).
- Methi / Menthi - Small, Small Methi, kothimeera / Coriander, Thotakura / Amaranthus, Pudina / Mint, Chukkakura, Ponaganti, Gongura / Sorrel Leaves, spring onion, Bachali — bought and counted in PIECES directly by the vendor (backend unit "pc"), confirmed across multiple vendor messages, despite no "1 Pc" marker in items.txt. Unlike Curry leaves (below), these are NOT bought as one bunch that gets split into priced sub-units — there is no bunch-to-piece derivation for these at all. The message's own piece count IS the quantity, used as-is.

LEAFY GREENS/HERBS — DO NOT FABRICATE A pc/kg RATIO: unlike a lemon or coconut (a whole piece with a real, fairly consistent average weight), one piece of a leafy green/herb has no reliable fixed weight — pieces vary too much for any pc/kg estimate to mean anything. If a message reports one of these (or a leafy green/herb not yet in the table above) in "pc", do NOT invent a conversion factor and force it into kg. Trust the message's reported pc count directly (no unit_mismatches entry needed — this isn't a real mismatch), and if it's a new herb not in the table above, still record it as pc as reported, then add it to the table above for next time. This applies specifically to leafy greens/herbs; it does not extend to whole-piece produce (fruits, tubers, etc.), which the general "estimate a conversion factor" mismatch-handling still applies to normally. Note the ONE exception is Curry leaves / Karvepaku (see QUANTITY DERIVATION below), which is genuinely bought as a single bunch and split into smaller priced units at a fixed rate — that is a different, deliberately separate mechanism from this rule and does not apply to any of the other herbs listed above.

VICTORY/KIRANA ITEMS — DIFFERENT DEFAULT, "pc" NOT "kg": Kirana items.txt entries never carry a "1 Pc" marker (none of them are named that way), so the produce default above would wrongly classify every single one as weight-based. It does NOT apply to them. Instead: Kirana items default to backend unit "pc" (one package/unit = 1 pc), full stop. A weight embedded in the item's own name (e.g. "Sugar Chips 100 Gm", "Rice (Victory) 1 Kg") describes the PACKAGE SIZE printed on that product, not an instruction to track it by weight — do not use that number to "convert" the invoice's piece count into kg. Trust the invoice's own "per" column: when it says "Pcs"/"Pac", record unit "pc" with the invoice's own quantity, with NO conversion and NO unit_mismatches entry — that is not a mismatch, it's already correct. Only treat a Kirana line as kg-based when the invoice's OWN "per" column literally says "Kgs" (a handful of genuinely bulk/loose items, e.g. bare "Groundnuts", bare "Toor Dal") — for those, use unit "kg" with the invoice's stated quantity directly, again with no invented conversion factor. If you find yourself estimating a "kg per package" conversion factor for a Kirana item, stop — that is the exact mistake this paragraph exists to prevent.

Mismatch check, per line: backend "pc" but message gives kg -> mismatch (kg->pc). Backend "kg" but message clearly gives a discrete piece count, not weight -> mismatch (pc->kg). On mismatch, resolve in order:
1. MANUAL OVERRIDE TABLE (below) has this item -> convert with that factor, "conversion_source": "manual_override".
2. No override -> estimate a reasonable factor from general produce-weight knowledge (e.g. "medium lemon ~70-115g -> ~9-13/kg"), convert, "conversion_source": "estimated", and ALSO add it to "new_outliers_detected" so the user can promote it to a confirmed override.
Record the FINAL quantity/unit as the converted value always — "unit_mismatches" preserves the original wording for traceability. If units already agree, record as-is; do NOT apply an override just because the item is listed there — only an actual mismatch triggers it (e.g. Lemon has an override, but a message already reporting it in pc needs no conversion).

MANUAL CONVERSION OVERRIDES (edit over time):
- Lemon 1 Pc : 1 kg = 25 pc (user's actual vendor lemons; smaller than typical medium)
- Drumstick 1 Pc : 1 kg = 15 pc

===========================================================
QUANTITY DERIVATION — when the line doesn't give a usable quantity directly
===========================================================
Derive per the rule below instead of reading a quantity off the line, and note how in "warnings" (it's inferred, not stated).

Fixed price-per-unit — quantity = line_total ÷ known unit price:
- Curry leaves / Karvepaku: backend unit "pc", 4 rs/small bunch. quantity = round(line_total / 4). E.g. "Curry leaves - 100rs" -> 25 pc. Warning: "Curry leaves quantity derived as line_total / 4 rs per bunch, not stated directly."

Fixed-weight box items — trust a stated kg figure or box count if given; if the line gives only a line_total (neither), default to 1 box and flag it in "warnings":

| Item        | Box weight | Default (1 box) |
|-------------|-----------|------------------|
| Royal gala  | 18 kg     | 18 kg            |
| Pomogranate | 9 kg      | 9 kg             |
| Tomatoes    | 23 kg     | 23 kg            |

quantity = boxes × box weight when a box count is stated; = the stated kg figure when one is given directly; = box weight (1 box) when neither is given, e.g. "Pomogranate -2400" -> 9 kg, warning: "Pomogranate quantity assumed as 1 box x 9kg since only a line_total was given."

===========================================================
BUYING_PRICE_PER_UNIT — per-unit price, NOT the line total
===========================================================
"buying_price_per_unit" is always the PER-UNIT buying price typed into the price field — never the line total.
- Source gives only a line total (typical for WhatsApp messages): buying_price_per_unit = total ÷ FINAL quantity (after any unit conversion above). E.g. Lemon 3kg->75pc @200rs total -> buying_price_per_unit = 200/75 = 2.67, not 200/3.
- Source gives an explicit per-unit rate directly (e.g. a Victory invoice's Rate column): copy it as-is, don't divide again.
- Always also record "line_total" — the total paid for that line. Prefer the source's own stated total (message total or invoice Amount column) over recomputing it, since it's more authoritative than buying_price_per_unit × quantity (rounding drift). Compute buying_price_per_unit × quantity only if no total is given directly.
- "computed_total" sums every item's "line_total" (never "buying_price_per_unit") plus all "additional_charges". It does NOT include "unmatched_items" — those are tracked separately precisely because they couldn't be entered as real items.
- This same line_total-not-rate rule applies to "unmatched_items" too: when a source shows both a rate and a total for an unmatched line (e.g. a Victory invoice's Rate and Amount columns), record the TOTAL, never the rate — mixing the two up on even a handful of lines throws "computed_total" off by thousands, since rate is typically 10-50x smaller than the actual line total.

===========================================================
NON-ITEM CHARGES
===========================================================
Lines like "Transportation-Hamali-200rs" or "Hamali-220" aren't items — put them in "additional_charges": {"description": "...", "amount": ...}.

===========================================================
VALIDATION
===========================================================
"computed_total" MUST be a genuine, independent sum of "items" line_totals + "additional_charges" — arrived at by actually adding those numbers, never by copying "stated_total" (even when you expect them to match) and never by adjusting either number just to make them agree. Setting "computed_total" equal to "stated_total" without having actually summed the items is itself a bug, and one that hides real errors elsewhere (a wrong "line_total" on any item, or an item that silently didn't make it into the array).

Then compare the two. A gap is often EXPECTED, not an error: "stated_total" (a message's stated total, or a Victory invoice's tax-inclusive Total line) can legitimately include tax and/or unmatched-item amounts that "computed_total" (items + charges only, no tax) never counts. When they differ, quantify the gap in "warnings" and account for it (e.g. "gap of 2603.80 matches the invoice's IGST line — expected, since computed_total excludes tax" or "gap of 1327.62 = the sum of unmatched_items line_totals"). An unexplained gap, or a gap that's suspiciously exactly zero because computed_total was copied rather than summed, is not acceptable — either way, show the arithmetic.
